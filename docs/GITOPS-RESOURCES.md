# GitOps resources

`patronus gitops sync [--apply|--dry-run]` / `patronus gitops watch` (the
`patronus-gitops` service, `[gitops]` in patronus.toml) apply the YAML files under
the repository's `config_path`. Every document is
`apiVersion: patronus.firewall/v1`, a `kind`, `metadata.name` and a `spec`. The
engine keys its state by `metadata.name`, so **names must be unique across all
kinds** (`metadata.name` of an Alias and of a rule cannot be the same).
Resources are stored, then the owning applier pushes them to the system once per
pass; a resource that cannot be applied makes the whole pass fail and the store is
restored (`patronus gitops sync` prints the reason). Deleting a file removes what
it declared. Proof: `ci/netlab/lane-m-gitops.sh` (rules) and
`ci/netlab/lane-m-gitops-resources.sh` (everything below), README claims C38 and C61.

| kind | owner | spec |
|---|---|---|
| `FirewallRule`, `NatRule` | firewall | see `patronus_config::declarative`; `address: "$alias"` names an alias |
| `Alias` | firewall | `type: host \| port \| geoip \| urltable \| urltable_ports`, `entries` (addresses / ports / country codes / the URL), `url`, `refresh_secs`, `max_entries`, `description`, or `source: {kind: threat, url, direction}` for a threat feed (name `ti_<id>`) |
| `WireGuardTunnel` | wireguard | `listen_port, addresses, mtu, endpoint, client_dns, client_allowed_ips, enabled, description, peers: [{name, public_key, allowed_ips, endpoint, persistent_keepalive, preshared_key, enabled}]` |
| `IpsecTunnel` | ipsec | `remote_address, local_address, local_id, remote_id, psk \| psk_file, local_ts, remote_ts, ike_proposals, esp_proposals, start_action, dpd_delay, enabled` |
| `IpsecRoadWarrior` | ipsec | `auth: eap \| cert, server_id, pool, dns, local_ts, local_address, enabled, users: [{username, password \| password_file, enabled}]` |
| `Group` | accounts | `description, privileges: {firewall: write, vpn: read, ...}` |
| `User` | accounts | `role: admin \| operator \| readonly, password_hash, enabled, groups: [one group]` |

Rules of the road:

* **Secrets are not in git.** The WireGuard tunnel's private key is generated by
  Patronus; a peer without `public_key` is a road warrior whose key pair is
  generated. IPsec pre-shared keys and road-warrior passwords can be read from a
  file on the box (`psk_file`, `password_file`: an absolute path, read when the
  resource is applied); a *new* tunnel / EAP user needs one of the two, an existing
  one keeps its secret when neither is given. A `User` carries only the argon2 hash:
  `printf '%s\n' "$PASSWORD" | patronus users hash-password`.
* **Lists are authoritative.** The `peers` of a WireGuardTunnel and the `users`
  of an IpsecRoadWarrior are the complete lists: members not listed are removed.
* **Self-filling aliases** (URL table, GeoIP, threat feed) start empty; the sync
  fetches them right after the apply (and `patronus gitops watch` / patronus-web
  keep refreshing them), an update keeps the entries already fetched.
* **Accounts are guarded:** the repository cannot delete, demote or disable the last
  enabled admin; a new `User` needs `password_hash`; a user's group must exist
  (declare the `Group` too: groups are created first and removed last).
* OpenVPN, L2TP, LDAP/RADIUS servers and API keys are not GitOps resources yet
  (API keys are secrets by nature); manage them on their pages.
